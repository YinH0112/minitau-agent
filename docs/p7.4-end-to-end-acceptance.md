# P7.4：完整 Agent 场景验收

P7.4 不再新增一套 Agent loop，而是把已有组件串成一次真实的离线工作流，验证它们组合后仍然满足 Agent 的核心生命周期。

## 验收场景

`tests/test_p74_end_to_end.py` 覆盖两条主路径：

1. FakeProvider 先要求 Agent 调用 `read`，再调用 `write`、`edit` 和 `bash`。每次工具返回后，loop 都会把 `ToolResultMessage` 放回上下文，再请求模型生成下一步或最终回答。这验证了 ReAct 的“模型决定动作 → 工具执行 → 观察结果 → 继续推理”。
2. 文件修改完成后执行手动压缩，退出当前运行对象，再从 JSONL 快照恢复；恢复后继续提问，然后切回压缩节点创建分支。测试检查摘要、分支标记和恢复后的消息路径，确保其他分支内容不会混入。
3. 另一个场景让 `bash` 执行一个长时间命令。收到取消后，Agent 不会发起第二次模型请求；操作清理完成后，同一个会话仍能继续下一轮。

## 为什么使用 FakeProvider

每个模型事件流都是预先定义的，测试因此能精确知道哪次调用应该产生工具请求、哪次调用应该返回文本。它不会依赖网络、API key 或模型的随机决策，但仍然经过真实的 `CodingSession`、`AgentHarness`、`run_agent_loop`、工具执行、JSONL 存储、压缩和分支代码。

真实 Provider 的端到端冒烟仍应单独手工执行；离线验收负责证明 Agent 的内部数据流和资源生命周期。

## 运行方式

```shell
uv run pytest -q tests/test_p74_end_to_end.py
uv run pytest -q
uv run mypy src
uv run ruff check src tests
```
